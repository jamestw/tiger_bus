# 巴士調度派遣管理系統 — 設計文件

日期：2026-07-28

## 背景與現況

目前業務以手工試算表（Google Sheets）管理：
1. **行程總表**：多組並排區塊，每組欄位為「日期／行程（起訖地）／接單人／人數／司機」，用顏色標示不同客戶/接單人分類
2. **司機月結算表**：逐筆行程記錄車資、薪資、油資、過路費等收支，並混雜車輛每月固定成本（車體險、常年會費、每月貸款、年度評鑑費等），底部合計出當月淨利
3. **利潤總表**：逐月彙總金額，追蹤全年獲利趨勢

此系統的目標是把這套手工流程數位化：從行程建立、司機（車輛）指派、行事曆檢視派遣狀況，到月底統計司機趟數並產生結算金額、以及整體營運總覽。

## 目標使用情境

- **多租戶（多車行）SaaS**：一套系統服務多家車行（tenant），彼此資料互不可見
- `superadmin`（開發方/平台管理者）可跨車行查看與管理所有資料
- 每家車行內部再分四種角色：**車行管理者**、**調度接單**、**會計**、**司機**
- 使用方式為多人透過瀏覽器同時使用（辦公室人員用電腦，司機可用手機瀏覽器查看自己班表），不需要原生 App
- 上線初期建立一個「測試車行」供功能驗證

## 系統架構

- **前端／後端**：Next.js（React + TypeScript）monolith，伺服器端渲染 + API routes
- **資料庫**：PostgreSQL，透過 Prisma ORM 存取
- **驗證**：NextAuth（帳號密碼登入，未來可擴充 Email/第三方登入）
- **部署**：單一伺服器/容器（如 Docker + 一台雲端主機），不需要複雜的多區域架構
- **前端呈現**：純響應式網頁（RWD），不做原生 App

### 多租戶隔離策略

採用共用 schema，所有租戶相關資料表都有 `tenant_id` 欄位。由於選擇自架 PostgreSQL（而非有內建 Row Level Security 的託管方案），隔離的正確性完全依賴應用層邏輯，因此：

- 建立一個共用的「租戶感知資料存取層」（tenant-scoped repository/data-access layer），所有一般查詢**必須**透過這層存取，該層自動依目前登入者的 `tenant_id` 加上過濾條件
- 禁止在業務邏輯程式碼中直接對 Prisma client 發出未經此層過濾的查詢（`superadmin` 專用的跨租戶查詢走獨立、明確標記的路徑，不共用一般查詢路徑，避免誤用）
- 這個限制本質上是團隊/程式碼審查規範，設計上刻意讓「忘記過濾」變得不順手（例如一般查詢介面不直接暴露原始 Prisma model，只暴露已綁定 tenant 的版本）

## 資料模型

| 實體 | 說明 | 關鍵欄位 |
|---|---|---|
| **Tenant** | 車行 | 名稱、聯絡資訊 |
| **User** | 登入帳號 | 帳號、角色（superadmin/車行管理者/調度接單/會計/司機）、所屬 Tenant（superadmin 不綁定） |
| **Driver** | 司機 | 姓名、聯絡方式、預設車輛（關聯 Vehicle）、關聯登入帳號（選填） |
| **Vehicle** | 車輛 | 種類、車號、乘客數、最後檢驗日期、所屬司機（可換綁） |
| **VehicleFixedCost** | 車輛月固定成本 | 掛在 Vehicle 下，動態項目：名稱、金額、月份（如車體險、常年會費、每月貸款、年度評鑑費） |
| **Client** | 客戶（下單單位） | 名稱、聯絡方式 |
| **Trip** | 行程 | 開始日期、結束日期（支援跨天）、起訖地描述、客戶（關聯 Client）、人數、接單人（關聯 User，限調度接單角色）、司機（關聯 Driver）、狀態（待確認/已確認/已完成/已取消）、色標分類（依客戶或接單人自動決定） |
| **TripLineItem** | 行程動態收支項目 | 掛在 Trip 下，類型（收入/成本）、名稱（車資、油資、過路費…自由新增）、金額 |
| **SettlementRecord** | 結算單 | 某司機、某月份，彙總收支與車輛固定成本，應付金額，狀態（未結算/已產生/已付款——已付款為人工標記） |

### 關係說明

- Driver 與 Vehicle 分開建立，Driver 綁定一台預設 Vehicle；指派行程時選擇 Driver，系統自動帶出目前綁定的車號。若需換車，須先到司機管理頁面變更該司機的預設車輛，指派畫面本身不提供臨時換車
- 一趟 Trip 只對應一位 Driver（不支援單趟多司機）

## 核心工作流程

1. **建立行程**：調度接單人員新增 Trip，填開始/結束日期、客戶、人數、路線備註，狀態預設「待確認」
2. **指派司機**：選擇 Driver，系統自動帶出其綁定車輛與車號
3. **行事曆檢視**：提供兩種可切換的檢視，資料同步
   - **司機為欄**（甘特圖式）：橫軸司機、直軸日期，適合看誰有空、誰滿檔。跨天行程的色塊橫跨多個日期格且中間不斷開
   - **月曆式**：每天一格，列出當天所有行程，適合看單日/單週整體出車量。跨天行程會在涵蓋的每一天格子都列出（標註第幾天），但都指向同一筆 Trip
4. **登錄收支項目**：行程進行/結束後，調度或會計人員在 Trip 下新增實際發生的 TripLineItem，項目不固定、用多少填多少。跨天行程的收支整趟登錄，不逐天拆分
5. **月結算**：會計於月底針對某司機、某月份，一鍵彙總「該月所有已完成 Trip 的收支項目」+「該司機綁定車輛當月的固定成本」，產生 SettlementRecord 與應付金額。若 Trip 橫跨月份邊界，整筆歸入 **開始日期** 所在月份，不做跨月拆帳。付款後由會計人工標記「已付款」（系統不串接金流或自動匯款）
6. **整體營運總覽**：比照手工「利潤表」，逐月彙總車行（或全平台，superadmin 可跨車行）的總收入、總成本、淨利趨勢

## 範圍界定

### 這次會做（MVP）

- 多租戶架構（Tenant/車行）與五種角色權限
- Driver、Vehicle（含固定成本）、Client、Trip 的完整 CRUD
- 行事曆雙檢視（司機為欄／月曆式），支援跨天行程
- 行程動態收支項目登錄
- 月結算單產生（單一司機/單一月份）
- 全車行 + 全平台（superadmin）營運總覽
- 建立一個「測試車行」供功能驗證

### 這次先不做

- 原生手機 App（先用響應式網頁）
- 金流/銀行自動匯款串接（結算僅計算金額，匯款人工操作，人工標記已付款）
- 客戶端自助訂車介面（客戶資料僅供內部登記使用）
- 車輛保養/驗車到期提醒通知
- 簡訊/Email 自動通知司機新行程

## 待確認的技術細節（實作規劃階段處理）

- Trip 狀態流轉的確切規則（例如誰能把「待確認」改成「已確認」）將在實作計畫階段細化，屬於既有權限矩陣的延伸，不影響本設計的整體架構
- 色標分類的自動指定邏輯（依客戶或接單人）將在實作時定義固定色票對應規則
